# `net` do Kof — frente de rede unificada (TCP + UDP)

## 0. Contrato (congelado por `D-KOF-NET`, votos regra-6 da mantenedora 01/10)

UM namespace `kof.net` (ao lado dos acessores URI que já vivem nele). Verbos bloqueantes; `spawn` é a única concorrência. Payload `Byte[]` nas duas mãos, nos dois transportes. UDP endereçado por String `"host:port"`; limite de datagrama 64 KiB com recusa `NET00x`; unicast-only no v1; política = modelo `app.security` existente; troca de chaves (`SECN005`) é decisão de superfície SEPARADA.

```
// TCP (conexão)
net.listen(port: Int) -> Listener
listener.accept() -> Conn              // bloqueia
net.connect(host: String, port: Int) -> Conn
conn.send(data: Byte[]) -> Int         // bytes escritos
conn.receive(maxBytes: Int) -> Byte[]  // bloqueia até um read; len-0 => fechado
conn.close() ; listener.close()
// UDP (datagrama)
net.bind(port: Int) -> Endpoint
endpoint.sendTo(addr: String, data: Byte[]) -> Int
endpoint.receive(maxBytes: Int) -> Byte[]   // um datagrama; origem guardada para peer()
endpoint.peer() -> String                   // "host:port" do último receive, "" antes
endpoint.close()
```

**Superfície como POUSADA (fatias 1–3)**, que é o contrato congelado acima: `receive` num endpoint devolve `Byte[]` (um datagrama) e a origem é lida por `peer()` — a sonda da fatia 1 resolveu a questão aberta do record `Datagram` pela forma escalar (sem record novo; `peer()` espelha o precedente de acessor de handle de `db`/`orm`). `sendTo` é o verbo de envio UDP. O tipo do receiver (Listener/Conn/Endpoint) é imposto em compile-time, então `send` não pode ser chamado num endpoint nem `sendTo` num conn.

## 2. Fatias (cada uma = reivindicar-commit-testar-push, RED-first)

1. ~~**Sonda de compilação do contrato (JVM)**~~ — **POUSADA 01/10.** Faces registradas em `KofNet` (`staticMethod` + `instanceMethod`, handles como 1º argumento como `web`/`db`) e em `MemberCallNamespaces`; descritores JVM em `JvmRuntimeCallDescriptors`/`JvmRuntimeReturnDescriptors` (13 casos `kof_net_*`, medidos corretos no `javap`). Códigos: `NET002` = verbo de socket sem runtime. **Verde falso medido fechado:** a sonda provou que `javap KofRuntime.class` tinha só os 8 verbos de URI + `split` — NENHUM `kof_net_listen` — então aceitar no JVM era um verde de compilação que morreria `NoSuchMethodError` no class load. A costura `KofNet.socketRuntimeReady` (via `KofNet.supportedOn` + `lowerNet`) devolvia `false` para todo verbo de socket em TODO alvo — virada na fatia 2 no instante em que o runtime gerado passou a carregar os métodos. Prova: `NetSurfaceE2ETest` 7/7, `StdCatalogTest` 11/11, `StdCatalogSignaturesTest` 13/13, `ConformanceMatrixTest` 14/14, `KofNetTest` 4/4 (1 skip de ambiente).
2. ~~**Runtime JVM + TCP + UDP E2E**~~ — **POUSADA 01/10.** `JvmRuntimeSockets` (fragmento novo ligado ao `JvmRuntime`, `java.net` só dentro dele — mesma higiene do `JvmRuntimeWebServer`) emite os três handles reais (`NetListener`/`NetConn`/`NetEndpoint`) e `kof_net_listen/accept/connect/bind/send/receive/sendTo/receiveFrom/peer/close`. TCP: `ServerSocket`(SO_REUSEADDR)→`accept`→`Socket` eco de fluxo com worker `spawn`; UDP: `DatagramSocket` bind/send/receive com a origem capturada para o `peer()`. **Dois defeitos medidos corrigidos:** (a) o `receive` enchia `maxBytes` em laço — DEADLOCK para qualquer protocolo interativo; agora volta assim que HÁ dado (semântica de `read`), `[]` no EOF, e o framing acumula em Kof; (b) o limite de datagrama `65535` passava no front mas o SO respondia "mensagem muito longa" — o limite honesto é o do PAYLOAD UDP/IPv4 `65507` (= 65535 − 20 IPv4 − 8 UDP), recusado por nome como `NET003` ANTES do syscall. O virar do portão está acoplado à existência do método. Prova: `NetTcpE2ETest` 9/9, `NetSurfaceE2ETest` 7/7, `KofNetTest` 4/4.
3. ~~**Front Native x86-64**~~ — **POUSADA 01/10.** `NativeNetFront` (+`NativeNetFrontTcp`/`NativeNetFrontUdp`/`NativeNetFrontPeer`) emite os dez verbos `kof_net_*` sobre handles opacos do heap (`tag` 1=Listener/2=Conn/3=Endpoint; `fd`; `hasPeer`+última origem). `net.listen` = SOCK_STREAM+SO_REUSEADDR→bind→listen; `accept`; `net.connect` = SOCK_STREAM+`kof_plat_net_connect` (só IPv4 dotted-quad, v1); `net.bind` = SOCK_DGRAM; `send`/`receive` sobre o fd do fluxo; `sendTo`/`receiveFrom` via syscall crua `sendto(44)`/`recvfrom(45)` com a origem capturada; `peer()` monta `"a.b.c.d:port"` com `kof_int_to_string`+`kof_string_concat`; `close` polimórfico por tag (tag errada = NET005). **Costura liberada:** `RuntimeNet` largou os `kof_net_bind/listen/accept/close` sem consumidor (medido por grep) e os dois chamadores de `kof_net_close` (MySQL `RuntimeDb4`, HTTP nativo `NativeHttpCore`) passaram a `kof_plat_close`. Prova: `NetNativeE2ETest` 6/6, `NetTcpE2ETest` 9/9, `NetSurfaceE2ETest` 7/7, `KofNetTest` 4/4.
4. **Ponte de host JS (4a) + portes cross (4b)** —
   **4a POUSADA 01/10.** O alvo JS é GraalJS-em-JVM com um mapa de host `kof_platform` (`KofJsRunner.exposePlatform`), não um subprocesso node; a ponte usa o MESMO `java.net` do runtime JVM. `JsRuntimeUiNet` ganhou os dez wrappers `kofNet*` (erros do host normalizados para `String` para que `catch (String m)` veja a mesma mensagem do JVM), `KofJsNetBridge` instala `netListen/netAccept/netConnect/netBind/netSend/netReceive/netSendTo/netReceiveFrom/netPeer/netClose` no mapa da plataforma, e `KofNet.supportedOn`/`socketRuntimeReady` aceitam `Target.JS`. Mesma semântica de `JvmRuntimeSockets`: receive volta assim que há dado, `[]` no EOF, `NET003` em 65508, `NET004` em endereço malformado, `NET005` em tag errada, `close` polimórfico. Prova: `NetJsE2ETest` **6/6** (ida-e-volta UDP + `peer()` real, NET003, NET004, todo verbo resolve, connect a porta morta recusa, oráculo URI inalterado) + `KofJsHostlessRuntimeTest` **3/3** (hostless/navegador: `net.listen` dá o erro honesto do shim `not available`, nunca `ReferenceError`). **Limite medido:** `spawn` no JS é uma Promise de mesma thread (`JsRuntimeUiLayout.kofSpawn`), então um `accept()` bloqueante do host dentro de `spawn { }` não corre em paralelo — a concorrência TCP server-side no JS NÃO é honestamente provável no modelo JS atual (a ida-e-volta UDP não precisa de concorrência; o eco TCP real é provado no JVM + Native).
   **4b POUSADA 02/10.** O front x86 (`NativeNetFront*`) foi portado para asm riscv64: `NativeRiscvAsmNetCore` (helpers + HAL `kof_plat_net_bind/listen/accept/send` + listen/accept/connect/close), `NativeRiscvAsmNetTcp` (send/receive) e `NativeRiscvAsmNetUdp` (bind/sendTo/receiveFrom/peer + `parse_host`/`udp_check`). Mesmo layout de handle opaco de 48 bytes e mesma semântica do x86; `NativeRiscvNetEmit` condiciona a emissão ao programa chamar um verbo de socket. O aarch64 herda linha-a-linha pelo `NativeAarch64Translator` (syscalls asm-generic: bind=200 listen=201 accept=202 sendto=206 recvfrom=207 setsockopt=208). O portão `KofNet.supportedOn`/`socketRuntimeReady` aceita `NATIVE_RISCV64`/`NATIVE_AARCH64`. **Correção de toolchain:** os binutils cross ESTÃO no host de dev em `~/.local/share/kof-cross` (precisa de `KOF_CROSS_SYSROOT` + `LD_LIBRARY_PATH`); a nota anterior de "ausente" estava velha. Prova: casos cross do `NetNativeE2ETest` (eco TCP byte-a-byte com worker `spawn`, ida-e-volta UDP + `peer()` real, todo verbo resolve no LINK) verdes sob **qemu-riscv64 E qemu-aarch64**; `NetSurfaceE2ETest`/`NetTcpE2ETest` agora afirmam que o cross BINDA.
5. ~~**Script + decisão do navegador + corpus**~~ — **POUSADA 02/10 (face Script + corpus).** Medido: `prepareForInterpretation` faz o lowering do Script com `target = JVM` e o interpretador reflete o MESMO `KofRuntime` gerado — todo verbo de socket é REAL no Script pelo corpo JVM (paridade por construção), provado RED-first: `NetScriptE2ETest` **3/3** (eco TCP com payload `new Byte[4]` + worker `spawn`, round-trip UDP com `new Byte[3]` + `peer()` real, recusa `NET003` do datagrama gigante via `catch (String)` do Kof). **A sonda achou o BUG GÊMEO DO §185 no interpretador:** `KofInterpreterOps.newArray` não tinha os casos `byte`/`short` (`new Byte[n]` → `int[]`) e `KofInterpreterValues.coerceFor` agrupava `byte,short` com `int` (Integer no `Array.set` de `byte[]` → "argument type mismatch") — invisível até a D-KOF-NET criar o primeiro consumidor real de `Byte[]` no runtime. Corrigido na raiz (byte/short materializam `byte[]`/`short[]` e coagem para `Byte`/`Short`); prova `KofInterpreterParityTest#byteShortArrayStore` 27/27 (borda com sinal 200 envolve igual ao JVM). Corpus: `training/idioms/net.md` (+PT) — contrato, idiomatico eco/UDP, regras, diagnósticos, verificado-por; `stdlib.md` (+PT) §net com a referência cruzada. **Navegador:** NÃO existe distinção node/navegador em compile-time (`Target` tem um só `JS`) — o mecanismo honesto segue o erro de runtime do Proxy `kof_platform` (R7, provado em `KofJsHostlessRuntimeTest`); um seletor de plataforma é decisão DA MANTENEDORA (fila).

6. **Tipos de handle como nomes declarados (adendo)** — **POUSADA 02/10 (`74f956575`).** A superfície congelada sempre NOMEOU os handles (`net.listen -> Listener`, `accept -> Conn`) mas eles eram anônimos para a gramática de TIPOS DECLARADOS (checker §251): `Int pump(Conn c)` morria SEM011, forçando todo programa de produto a inlinear o trabalho de socket em `var`+closures. O core de transferência do KofShare (D-KOFSHARE-100KOF) é código de produto que não pode ser escrito assim (helpers de streaming recebem conexões). Correção = o padrão ui do §179: `KofNet.typeByName` mapeia `Listener`/`Conn`/`Endpoint` para os `ClassType`s `KofRuntime$Net*` já existentes, registrado via `CompilerTypes.builtinDeclaredType`; o guard de shadow é herdado (um `Conn` declarado pelo usuário vence). Prova RED-first: `NetHandleTypesE2ETest` **2/2** — um programa, os três tipos de handle como parâmetros + `Conn` como valor de retorno, executado em Script e JVM (pré-fix 4× SEM011); bateria de coexistência 60/60 na árvore compartilhada. Corpus: `training/idioms/net.md`(+PT) ganhou a regra do helper tipado. Consumidor provado: `transfer.kf` do KofShare (`946784d`, primeiro código de produto passando handles entre funções; E2E 200000 bytes TCP com resume@100000, byte-a-byte, verde em `--target jvm` E `--target script`).


7. **Emenda de decisão do alvo JS (D-NET-JS-V1)** — **POUSADO 02/10.** Voto múltiplo da mantenedora: opção "(c) kof.net fora do JS no v1". O front de rede é RECUSADO em tempo de compilação no `Target.JS` com `NETN001` — emitido em `import kof.net` (e `net.*`) em `CompilerPipeline.lowerToIR` E em chamadas nuas `net.<verbo>` / métodos de handle em `MemberCallNamespaces`. A antiga ponte host-JS da fatia 4a é retirada da superfície de linguagem (a ponte interna de runtime fica como defesa de profundidade, mas nenhum fonte de usuário compila para alcançá-la; o antigo `NetJsE2ETest` aposentado). A questão do seletor browser vs Node no compile MORRE — `D-JS-PLATFORM-SELECTOR` vale para outras superfícies de runtime; rede nunca vira artefato no JS. Prova RED-first: `NetJsV1RefusalE2ETest` **3/3** (chamada nua recusa NETN001, import recusa NETN001, controles JVM/JS-puro verdes; pré-fix 2/2 vermelho); `NetSurfaceE2ETest` + `NetTcpE2ETest` atualizados para afirmar a recusa; perna de rede do `KofJsHostlessRuntimeTest` afirma recusa no compile em vez do proxy de runtime.

8. **NET1 — resolução de nome + connect a um endereço validado (`D-MAINT-BATCH-0510`/NET1, issue #759)** — **POUSADA 05/10 (JVM/Script + Native x86-64 + riscv64/aarch64).** A primitiva de política de egresso que o issue pediu: `net.resolve(host) -> List<String>` (todos os endereços A/AAAA, na ordem do SO) mais `net.connect(host, port, address) -> Conn`, que disca o endereço NUMÉRICO já validado pelo chamador mantendo `host` para Host/SNI/cert — assim uma guarda resolve uma vez, valida cada endereço contra a política e conecta ao validado (sem re-resolução, anti DNS-rebinding). `JvmRuntimeSockets` carrega `kof_net_resolve` (`InetAddress.getAllByName`, host desconhecido lança `String` catchável, NET004) e `kof_net_connect_addr` (endereço em branco recusa NET004; `host` é inerte, espelhando o propósito SNI/Host); os descritores JVM e o `StdCatalog` ganharam as duas faces. **Native (x86-64 `NativeNetFront`, riscv64/aarch64 `NativeRiscvAsmNetCore`) usa libc `getaddrinfo`/`inet_ntop`** (link-por-uso: os três símbolos entraram em `NativeCrossLink.LIBC_SYMBOLS`, então um consumidor do resolvedor liga dinamicamente; medido — a libc do sysroot cross exporta os três), monta o `List<String>` com `kof_list_new`/`kof_list_add` + `kof_string_from_literal`; `connect_addr` disca o dotted-quad validado pela rota de connect existente. O JS recusa a frente inteira com `NETN001` (`D-NET-JS-V1`). Prova RED-first: novo `NetResolveE2ETest` **6/6** (pré-fix 3/4 RED, `SEM025 Cannot resolve method 'resolve'/'connect' on namespace 'net'`) — resolve devolve os endereços de localhost e recusa um host desconhecido por nome, o connect de 3 args validado faz ida-e-volta de eco TCP, endereço vazio recusa, JS recusa `NETN001`; o mesmo programa roda em Native x86-64 e sob qemu-riscv64 + qemu-aarch64 (0 pulados no host de dev). Vizinhos verdes: `NetSurfaceE2ETest` 7/7, `NetTcpE2ETest` 9/9, `NetNativeE2ETest` 9/9, `KofNetTest` 4/4 — bateria net **43/43**.

O seletor de navegador em compile-time na fila também é decisão separada da mantenedora.
