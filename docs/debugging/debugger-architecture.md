# DEBUGGER_ARCHITECTURE.md — Kof Debugger Architecture

**Status:** Phases 1-3 implemented (DebugInfo in the IR, JVM metadata, `kof-debug` MVP)
**Date:** August 27, 2026
**Version:** 0.6.7 (7 targets; free-list + pthread spawn + FP XMM)

---

## 1. Principle

> **The programmer debugs the Kof program, never the intermediate artifact
> generated by the backend.**

The debugger preserves the Kof semantic identity over any target:

```text
Kof Source
    ↓
Debug Metadata (in the IR)
    ↓
Kof Debug Information
    ↓
Debug Adapter (DAP)
    ↓
Editor
```

Each backend translates the Kof debug model to the platform format
(JDWP/DWARF/Source Maps) — but the public abstraction is always Kof.

## 2. Division of responsibilities

| Layer | Responsibility |
|--------|------------------|
| Frontend | AST with source positions |
| CompilerDriver | **Debug Metadata** — each IR op knows where it came from |
| IR | KofDebugInfo (source files, functions, locals, scopes, mappings) |
| JvmBackend | LineNumberTable, LocalVariableTable, SourceFile |
| NativeBackend | symbols, line tables (DWARF ✅ x86-64 + cross) |
| JsBackend | Kof → JS source maps (function-level) |
| kof-debug | Debug Adapter (DAP) |
| Kof Editor | breakpoints, stack, variables (DAP) |

## 3. Debug Metadata in the IR

Every relevant Kof IR operation carries the relation:

```text
IR instruction
 ├── source = src/UserService.kf
 ├── line = 42
 ├── column = 17
 ├── function = UserService.find
 └── scope = method
```

The internal model (backend-agnostic), implemented:

```text
KofDebugInfo(positions)
 └── Map<KofOperation, SourcePosition>   (op identity → file/line/column)

IRMethod  →  carries KofDebugInfo
IRModule  →  carries the source file name (SourceFile)
```

The position is recorded **in the frontend** while the body is lowered
(statement → op range), never synthesized in the backend — the backend
only translates.

Do not create JVM-specific metadata — the source information exists
**before** the backend.

## 4. Mapping per target

| Target | Native format | User-facing exposure |
|--------|----------------|----------------------|
| JVM | LineNumberTable, LocalVariableTable, SourceFile + JDWP | Kof functions and lines |
| Native | symbols + line tables (DWARF ✅ x86-64 + cross) | Kof functions and lines |
| KofJS | Kof → JS source maps (function-level) | Kof functions and lines |

## 5. Rules

- Never: `Kof → Java → debugger`
- Never: show JVM slots, assembly or generated JS as the primary experience
- Synthetic code (generated constructors, lambdas, accessors) must be
  **hidden** — the user sees the original Kof abstraction
- `--debug` build preserves extra metadata; `--release` does not destroy essential
  metadata without need

## 6. Phases

```text
Phase 1  DebugInfo in the IR (source location per op)             ✅
Phase 2  JVM: SourceFile + LineNumberTable + LocalVariableTable   ✅
Phase 3  kof-debug MVP: DAP over stdio + raw JDWP                 ✅
        (launch, breakpoints by Kof line, stopped, stack trace
         with Kof functions/lines, continue, disconnect)
Phase 4  Kof Editor: breakpoints, toolbar, call stack, variables, stepping
Phase 5  Native: DWARF + DAP↔gdb/MI2 bridge + attach              ✅ (X7-1..X7-5)
Phase 6  JS: source maps + Node Inspector                         partial
        (map emitted but function-level; Node Inspector = honest gap —
         embedded GraalJS engine, see `debugging-js.md`)
Phase 7  Advanced: per-frame locals, stepping, conditional/exception
        breakpoints, evaluation, async                            partial
        (Native and JVM: locals/scopes/stepping/evaluate/exception
         breakpoints + pause — 20/09; remaining: conditional breakpoints,
         async; the JS face is an honest gap)
```

Implementation details of `kof-debug` (Phase 3): see `debug-adapter.md`.
